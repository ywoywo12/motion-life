# الهيكلية التقنية

## لماذا Flask وليس Next.js/Prisma؟

البرومبت اقترح Next.js + Prisma + PostgreSQL «أو مكافئ موثوق». بيئة البناء **تحجب مستودعات الحزم (npm وPyPI)**؛ فشلت محاولات `npm view` و`pip` بسبب سياسة الشبكة. لذلك اعتمدنا أدوات **مثبتة مسبقاً ومستقرة**:

| الطبقة | الاختيار | السبب |
|---|---|---|
| الخادم | Python 3 + **Flask 3.1** (Werkzeug/Jinja2) | ناضج، وتحقق الصلاحيات على الخادم مباشر |
| قاعدة البيانات | **PostgreSQL 16** | مطلوبة في البرومبت. قيود وفهارس وTriggers لحماية السجل |
| الوصول لقاعدة البيانات | SQL صريح بمعاملات مربوطة عبر **libpq** (`app/pq.py`، ctypes) | لا يوجد مشغّل Python مثبت. libpq هي مكتبة العميل الرسمية (مصادقة SCRAM/TLS)، والمعاملات تُربط على الخادم (لا دمج نصوص). **في الإنتاج يُفضَّل `psycopg`**، و`app/db.py` يستخدمه تلقائياً إن وُجد |
| الهجرات | ملفات SQL مرقّمة + `scripts/migrate.py` | شفافة وقابلة للمراجعة |
| الواجهة | قوالب Jinja (RTL) + JavaScript بلا مكتبات | لا حاجة لأداة بناء، وتعمل مع CSP صارم (`script-src 'self'`) |
| PDF | Chromium (Playwright) يطبع HTML عربياً | تشكيل عربي واتجاه نص صحيحان، دون مكتبة PDF تحتاج معالجة bidi يدوياً |
| الاختبارات | `unittest` (مدمجة) + Flask test client + PostgreSQL اختبارية منفصلة | — |

## البنية

```
app/
  __init__.py        create_app: جلسات، CSRF، رؤوس أمان، معالجة أخطاء دون تسريب PHI
  config.py          الإعدادات من البيئة/.env
  pq.py, db.py       الوصول لقاعدة البيانات + معاملات (transaction لكل طلب)
  security.py        كلمات المرور (scrypt)، القفل، الجلسات (رمز مجزأ في قاعدة البيانات)
  rbac.py            الأدوار والصلاحيات ونطاق المريض (شرط SQL)
  audit.py           سجل تدقيق إلحاقي
  validation.py      تحقق المدخلات برسائل عربية
  clinical/          definitions (الأسئلة) · engine (التفرع والتحقق) · safety (القواعد) · catalog_seed (الاختبارات والأجهزة والمقاييس)
  services/          منطق الأعمال: كل دالة تتحقق من الصلاحية ثم القواعد ثم تكتب وتدقّق
  web/               api.py (JSON) · pages.py (صفحات GET) · reports.py (PDF) · filters.py
  templates/, static/
migrations/          SQL
scripts/             migrate, seed, demo_data, backup.sh, restore.sh, screenshots, smoke_flow
tests/               test_acceptance (معايير §11)، test_security، test_rules
```

## مسار الطلب

1. `before_request`:
   - يحل الجلسة من الكوكي (`HttpOnly; SameSite=Strict`).
   - لكل طلب غير GET: يفحص `Origin` ورمز CSRF.
2. الـ API تستدعي خدمة داخل `db.tx()`: معاملة واحدة، ويُتراجع عن كل شيء عند أي خطأ.
3. الخدمة تنفذ بالترتيب:
   - `require_perm`.
   - `load_*_scoped`، الذي يعيد 404 لأي سجل خارج النطاق دون كشف وجوده.
   - التحقق من المدخلات وقواعد الحالة.
   - الكتابة.
   - `audit`.

## حماية البيانات على مستوى قاعدة البيانات (دفاع في العمق)

| الحماية | الآلية |
|---|---|
| سجل التدقيق لا يُعدل ولا يُحذف | `audit_events`: trigger |
| لا حذف فعلي للسجلات السريرية | triggers على المرضى والإجابات والنتائج والإصدارات والقرارات والجلسات |
| الإصدار المعتمد مجمّد | محتوى الإصدار وبنوده لا يتغيران خارج حالة `DRAFT` |
| ربط الجلسة ثابت | لا يتغير ربطها بإصدار الخطة |
| لا اعتماد ذاتي | `CHECK (approved_by <> author_id)` |
| إصدار معتمد واحد | فهرس فريد: إصدار معتمد واحد ومسودة/مراجعة مفتوحة واحدة لكل خطة |
| إجابة حالية واحدة | فهرس فريد: إجابة حالية واحدة لكل سؤال ونطاق. القديمة تُعلَّم `superseded` |

## التزامن (Concurrency)

| النوع | الآلية |
|---|---|
| الهوية والمستخدمون | `version` (قفل متفائل)، وتُعاد 409 عند التعارض |
| مسودة الخطة | `lock_version` |
| الإجابات | لكل إجابة `base_id`. إن تغيّرت الإجابة على الخادم منذ آخر قراءة تُعاد في `conflicts` ولا يُكتب فوقها |
| تغيير حالة الخطة | `UPDATE … WHERE status = from_status` يمنع قرارين متزامنين |

## الحفظ في الواجهة

يعرض شريط الحفظ أربع حالات: «تعديلات غير محفوظة»، «جارٍ الحفظ»، «حُفظ ✓ + الوقت»، «فشل الحفظ + إعادة المحاولة».

- الإجابات غير المحفوظة تُنسخ إلى `localStorage` (على الجهاز نفسه). عند فتح الصفحة لاحقاً يُعرض «استعادة وحفظ» أو «تجاهل».
- لا تُعرض «حُفظ» إلا بعد ردّ ناجح من الخادم.
- يظهر تحذير المتصفح عند المغادرة مع وجود بيانات غير محفوظة.
